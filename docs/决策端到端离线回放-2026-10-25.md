# 决策端到端离线回放（2026-10-25）

> 目的：无真机时验证 `capture → YOLO → 小地图 → build_state → decide → trace` 全链路可跑，并定位主循环耗时分布。
> 口径：`--capture replay` 读 `data/matches/20261018_144334_007412/frames`（776 张关键帧，10Hz 调度），**不含 adb/窗口采集开销**；不代表真机帧率。

## 1. 命令

```bat
venv\Scripts\python.exe -X utf8 scripts\m2_agent_v2.py ^
  --capture replay --replay-dir data\matches\20261018_144334_007412\frames ^
  --replay-fps 10 --seconds 10 --decision-trace --yolo-every 1 --timing
```

## 2. 结果

- 20s 长跑：159 拍 / 感知 103 次 / 决策 103 帧；`in_match` 128 拍，`waiting` 31 拍。
- 10s 计时跑：44 帧，决策来源全部 `optimizer`（规则先出，优化器改写）。
- 决策耗时：rule avg 0.387ms / max 10.48ms；optimizer avg 0.459ms / max 0.98ms。
- 轨迹（44 帧）：decide p50/p95 = 0.6 / **0.9ms**；loop p50/p95 = 106.5 / **196.9ms**；capture_lag p95 **165.5ms**；infer p95 **65.7ms**。

## 3. 结论

1. **决策层不是瓶颈**：占 0.2%，p95 < 1ms；40ms 预算有大量余量。
2. **主循环瓶颈在取帧与渲染/检测**：`wait_frame` 54.5%、YOLO 18.7%、`render_live` 15.8%。回放采集本身有调度等待，所以 `wait_frame` 占比会被放大；但 `render_live` 31ms/帧是纯本机 CPU，值得作为下一步优化项（例如仅在 `--show` 时渲染）。
3. **端到端 loop p95 196.9ms**，刚好贴近 200ms（5Hz）预算；真要提到 10Hz 必须降低 YOLO/渲染耗时，而不是改决策。

## 4. 限制

- 关键帧 5s 一张，不能评估跟踪连续性/感知精度。
- 回放调度会注入等待，`wait_frame` 与 `capture_lag` 不等于 adb 实局。
- 不含 laya 推理；laya GPU 单次 92ms（见 `docs/决策延迟基准-2026-10-24.md`），必须留在决策临界路径外。
