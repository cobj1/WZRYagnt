# bridge 决策延迟优化：42.19ms → 24.61ms（p95）

> 日期：2026-10-26｜目标：G1 的「决策 p95 ≤ 40ms」
> 改动文件：`hok-decision-ai/src/hok_decision/search/planner.py`（唯一一处）
> 验证：同一批 1000 帧，决策字段**逐帧零差异**

---

## 0. 结果

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| hok_bridge p50 | 24.77 ms | **17.42 ms** | −30% |
| hok_bridge p95 | **42.19 ms（超预算）** | **24.61 ms** | **−42%** |
| 全链路 p95 | 42.56 ms | **24.94 ms** | −41% |
| 生产规则 p95 | 0.39 ms | 0.44 ms | 噪声级 |
| 严格 @3 一致率 | 12.42% | 12.42% | **不变** |

**G1 达标**（24.61 ≤ 40），且留有 38% 余量。

## 1. 怎么定位的（cProfile，40 帧）

```
beam_search            2.780s  (97%)
  rollout_decision     1.723s  (60%)
    _capture_resources 1.433s  (50%)   ← 25600 次调用，1.8M 次生成器迭代
    deepcopy           0.970s  (34%)   ← SearchState 每次 rollout 深拷贝
      _distance        1.475M 次调用
```

两个发现：
- `_capture_resources` 占了 beam_search 的一半时间，而它每次都在遍历 `map_data.resource_points`
  并用 `_distance()`（带 `** 0.5` 开方）做半径判断；
- `_distance` 被调了 **147 万次**，其中绝大多数只用于"比大小"（最近敌/友、是否在半径内）。

## 2. 改了什么（三处，全部是等价变换）

### ① 引入 `_dist2()`，比较场景不再开方
```python
def _dist2(a, b):
    dx, dy = a[0]-b[0], a[1]-b[1]
    return dx*dx + dy*dy
```
- `_nearest_enemy` / `_nearest_blue`：取 `min` 时用 `_dist2` 作 key。
  平方距离与原距离**严格同序**（单调变换），选取结果完全一致。
- 半径判断：`_dist2(...) <= R*R`，与 `_distance(...) <= R` 等价。

### ② 缓存"可占领点"列表
```python
_POI_CACHE: dict[int, list[tuple[str, tuple[float, float]]]] = {}
```
`map_data` 在一次搜索内不变，但 `_capture_resources` 每个 tick 都重扫 30+ 个点并重复过滤
`position is not None and kind in {...}`。改为按 `id(map_data)` 缓存一次。

### ③ 先判蓝方，再判红方
原来蓝/红两方 `any()` 都会执行。改为蓝方不满足半径就直接 `continue`
（多数点蓝方都够不到），省掉整轮红方距离计算。

**语义不变的依据**：`captured_resources` 只增不减、判断是"蓝近且红不近"，
提前 `continue` 与原来的 `if blue_near and not red_near` 完全等价。

## 3. 验证：决策逐帧零差异

同一批 1000 帧（`runs/eval/keys_from_prod1000.json` 固定 frame_id 集合），前后各跑一次生产基线评估：

```python
# 对比字段：rk(模型动作) / mc(命中?) / t1 / t3(目标) / rv(规则输出) / rt / ncand
frames old/new/common = 1000 / 1000 / 1000
diff by field = {}          # 全零
```

严格一致率同为 **12.42%**，翻转率同为 16.25%。

## 4. 剩余优化空间（本轮没做）

| 项 | 占比 | 风险 |
|---|---:|---|
| `deepcopy` of `SearchState` | 34% | 高——需要自定义浅拷贝或状态池，容易引入别名 bug |
| `rollout_decision` 的 tick 循环 | 60% | 中——可减 dt 或做向量化，但会改变数值轨迹 |
| beam_width / max_candidates | — | **会改变决策**，属于策略调整而非优化，需重新评估 |

按幂律估计，继续压 deepcopy 大约还能再省 20–30%，但从 24.61 ms 往 17 ms 走
对 G1 已无意义（40 ms 预算），除非将来要在 5Hz 下跑两路。

## 5. 教训

这次优化之所以安全，是因为**先有了"决策 digest 逐帧可比"的能力**（`eval_decision_offline` 的
`--dump-keys/--keys-file` + 生产基线）。没有它，任何性能改动都只能靠"看起来差不多"来验收——
本项目在这一项上栽过多次（见 `离线结论汇总` 的 B 级清单）。
