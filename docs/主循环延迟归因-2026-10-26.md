# 主循环延迟归因（2026-10-26，真机 + 真实对局帧）

> **配套**：根仓 `docs/数据专题/延迟归因-2026-10-26.md` 是同一晚另一次独立测量的记录
> （空载 28.5fps / +4 线程 17.7fps）。两份数字不同是**跑次差异**（负载机状态、相位时长），
> 结论一致：采集源不是瓶颈、4 线程以上才明显抢占。本文额外给出**优化前后四版对比**。
>
> 目的：把「`wait_frame` 占墙钟 88–97%」从一句结论拆成**可归因的分项账**，
> 并给出已落地优化的实测收益。
> 设备：MuMu 模拟器 `emulator-5554`（1080×1920 物理 / 游戏横屏 1280×720），adb root 可用。
> 帧源：`screenrecord`（live）与 `data/matches/20261017_162901_384146/frames`（回放，37 帧 20:9）。

## 0. 结论先行

| 结论 | 证据 |
|---|---|
| **采集源不是瓶颈** | 空载取帧 **27.4 fps**，加 2 个负载线程反而 28.8 fps |
| **GIL/线程抢占不是主因** | 4 个忙等线程只掉 23%（27.4→21.0） |
| **推理是第一个真实瓶颈** | 取帧+YOLO 掉到 **11.5 fps**（−58%） |
| **ORT 占满核在抢 CPU** | `--yolo-threads 4`：YOLO **55.1→36.0ms（−35%）**，小地图/渲染同步变快 |
| **小地图检测是第二大开销** | 优化前 28.2ms/次（占 19.1%），优化后 **11–13ms（−53%）** |
| **渲染在无消费者时白做** | `--no-annot --no-selfcheck` 下渲染占 13%，跳过即归零 |
| **`wait_frame` 96.8% 是空转假象** | 结算页上 `not_in_match 100%`，主循环只等帧 → 30fps，感知 0 次 |

## 1. 采集源归因（`bench_capture_load.py`，设备实时）

```
P1 只取帧            27.4 fps
P2 +1 负载线程        27.8 fps
P2 +2 负载线程        28.8 fps
P2 +4 负载线程        21.0 fps     ← 掉 23%
P3 取帧 + 推理        11.5 fps     ← 掉 58%
```

判读：A（采集源慢）**排除**；B（GIL 抢占）影响有限；**C（下游推理）是主因**。

> 注：本相位在结算页跑，画面静止，YOLO 的输入复杂度偏低，因此 P3 的 11.5fps
> 是**乐观值**；真实对局里 YOLO 单次 55ms（见下）。

## 2. 主循环分阶段（真实对局帧回放，`--capture replay`）

同一份 37 帧、`--replay-fps 10`、`--no-action`，三个版本对比：

| 阶段 | 优化前 | mm 优化后 | +threads4 | +跳过渲染 |
|---|---:|---:|---:|---:|
| 主循环拍数（/30s 或 /20s） | 261 / 30s = **8.7Hz** | 291 / 30s = 9.7Hz | 200 / 20s = 10Hz | 200 / 20s = 10Hz |
| `wait_frame` | 53.6ms (54.3%) | 57.7ms (63.2%) | — | — |
| 小地图 `tracker.update` | **28.2ms** (19.1%) | **13.2ms** (9.3%) | 9.2ms (5.6%) | 11.2ms (6.3%) |
| 渲染 `render_live` | 19.3ms (12.9%) | 18.7ms (13.1%) | 14.5ms (8.7%) | **0（跳过）** |

| 规则决策 `decide` | 0.4ms (0.2%) | 0.4ms | 0.4ms | 0.4ms |

> **回放测法的硬限制**：`--replay-fps 10` 把帧供给限在 10 fps，因此
> 9.7–10Hz 是**触顶值**，不是真实上限。要看真实上限必须用 live 对局
> （需有人在局内），本表只用于**同条件 A/B**——同一份帧、同样工作量，差异可信。

## 3. 已落地的两项优化

### 3.1 小地图检测 `detect()` 21.4ms → 12.0ms（−44%）

`cProfile` 定位：`ring_feat` 每次候选点做 2 次 `np.percentile`（140 次/帧）
与 `np.mgrid` 重建（1089 元素 ×3）。

- 新增 `_p90()`：与 `np.percentile(a, 90)`（linear 插值）**逐位等价**，
  用 `np.partition` 取代 numpy 通用 quantile 机制。1400 组随机数组验证 **0 不一致**。
- `_slope_sels()`：把 33×33 的内外环布尔掩码预计算一次，替换每点 `mgrid+sqrt`。
- `_ring_slope()` 复用同一对掩码。
- 验收：20 帧检测输出 **JSON 逐字节一致**（`/tmp/mm_before.json` vs `after`），
  耗时 21.4 → 12.0ms；端到端 `tracker.update` 28.2 → 13.2ms。

### 3.2 YOLO 线程数默认 0 → 4

同一份回放帧 A/B：`--yolo-threads 0` → 55.1ms，`--yolo-threads 4` → **36.0ms**。
且小地图（15.6→9.2ms）、渲染（18.3→14.5ms）同步变快 —— 说明 ORT 占满物理核
（本机 16 核）确实在跟主循环抢 CPU，这与 `wait_frame` 高占比的旧观察一致。

### 3.3 渲染按需执行

`render_live` 的产物只有三个消费者：窗口显示、标注 PNG、自我诊断截图器。
三者都关时（`--show` 关 + `--no-annot` + 新增 `--no-selfcheck`）直接复用原帧，
省掉 `frame.copy()` 与几十次 `cv2` 绘制。表中该阶段归零。

## 4. 仍待解决

1. **真实上限未知**：需要在 live 对局里跑一次 `--timing`（当前设备停在结算页）。
2. **YOLO 36ms 仍是最大单笔**：下一步可试 `--yolo-every 4/5`（降检测频率）
   或 OpenVINO/INT8；两者都要用同一份回放帧 A/B。
3. **`decide` 与 `optimizer` 已不是问题**（0.4 / 1.8ms），延迟预算应全部投给感知。
4. **回放不重建 `self_est`/冷却**，所以本表只用于归因，不能替代真机端到端验收（G1）。
