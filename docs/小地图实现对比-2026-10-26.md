## 2. 为什么 #2 是死路径（两处独立失效）

**失效一：后端层面恒空。** `detect_minimap` 只提取 `mm_red/mm_blue/mm_green/mm_yellow`
四类，而 m2 的默认检测器是 8 通用类的 `runs/detect/hok_yolov5/hok_yolov5s.onnx`
（`m2_agent_v2.py:1882`）。函数自身在 ONNX 后端下直接返回空：

```python
if self._hok is not None:
    self.last_mm_ms = 0.0
    return []
```

实测（默认模型、`conf=0.35`、10 帧真实对局图，裁剪 `frame[0:232, 0:232]`）：

```
model exists True
is_onnx_backend(_hok not None): True
detect_minimap total dets over 10 frames = 0
```

**失效二：裁剪坐标已脱钩。** 即使换成 `.pt` 11 类模型让它「有输出」，坐标也是错的：
`MMTrackerV7` 已按 `det["center"]/det["size"]` 反解裁剪原点（20:9 真机实测 `x=63`），
而 m2 的调用点仍写死 `frame[0:232, 0:232]`（`m2_agent_v2.py:2841`）。
两者原点不同，dots 归一化后的位置会整体偏移。

因此「有结果才覆盖」这段融合代码在默认配置下**从未生效过**，m2 的小地图点
100% 来自 `MMTrackerV7`。

## 3. 收敛步骤（按风险从低到高）

1. **`terrain.find_minimap_box`**：零生产引用，直接进零引用清单（与 §19-6 的 `_legacy` 同流程）。
2. **`detect_minimap` 融合块**：先在调用点加一行一次性告警
   （"ONNX 后端下该路径恒空，dots 全部来自 MMTrackerV7"），跑一周确认日志从不出现
   "非空覆盖"，再删融合块。**不要直接删函数** —— 保留 `.pt` 11 类后端的回退能力。
3. **`minimap.find_minimap` / `MinimapTracker`**：不在 m2 主路径，但 m1/m3/annotate
   仍在用。合并前必须先回答"这三条与 v7 的 dots 是否一致"，方法见方案 §5：
   用 `understanding_audit.py` / `m1_minimap_test.py` 在同一批帧上对比。
   **本次未做**（需要先有一个统一的 dots 序列化格式，属独立任务）。
4. **改名/搬文件**：禁止。外部脚本按名字引用（`demo_record`、`annotate`、`understanding`）。

## 4. 边界与未验证项

- 本文的"恒空"结论**只对默认 ONNX 后端成立**。若显式传 `--model *.pt`，
  `detect_minimap` 会真正推理，届时 §2 失效二（裁剪偏移）会立刻暴露成错误 dots。
- `MinimapTracker` 与 `MMTrackerV7` 的 dots 一致性**未测**。这是合并 #3/#4 的前置条件，
  不能因为"v7 是权威"就推断另外两条可以删。
- m2 的 `frame[0:232,0:232]` 在非 232px 小地图上还有边界风险（`mm["size"]` 可能不是 232）。
