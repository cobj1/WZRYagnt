## 2. 真机跑一场

```bash
# 先确认设备
tools/scrcpy/adb.exe devices -l          # 例: 192.168.0.103:5555  device  model:23013RK75C

# 真机（20:9）纯感知复测：只录数据、不下发任何操作
venv/Scripts/python.exe -X utf8 scripts/m2_agent_v2.py --seconds 240 \
    --capture scrcpy --no-annot --save \
    --no-action \
    --serial 192.168.0.103:5555 \
    --adb tools/scrcpy/adb.exe
```

- **`--save` 不能漏**：录制器是 `if args.save:` 门控的（`m2_agent_v2.py:3280`），
  **没有它就不会写 `data/matches/<ts>/states.jsonl`** —— 表现为"跑完 240 秒、日志一切正常、
  但 `--ls` 看不到新会话"。这是本清单初版的真实缺陷，已修正。
- **`--no-action`**：只感知不下发（日志里只有"决策:"、没有执行），适合在自己正打的局里做复测；
  去掉它才是真正接管操作。注意此模式下日志末尾会显示"模式: 模拟"。
- **`--capture scrcpy`**：`screencap` 曾把 3200×1440 强拉成 1280×720（纵向 1.25×），
  小地图被拉成非方形、`0.336×h` 的框边长随之失效。该缺陷已于 10-17 修复（改为长边缩到 1280、
  保持宽高比，实测同为 1280×576），但 **scrcpy 仍快 2.3×**（取帧 155ms vs 352ms），优先用 scrcpy。
- **`--no-annot`**：`render_live_analysis` 每帧写两张 PNG，实测 855ms/次，是 scrcpy 路径的新瓶颈。
- 时长建议 ≥ 240s。状态机进入 `in_match` 需"连续 90 帧**或** 3 秒"（`hold_s=3.0`，
  10-17 加的时长滞回；真机 6–9Hz 下 3 秒即进入，旧版按帧计数要 10–14 秒），所以别跑太短。
- 确认真机是 **1280×576（20:9）**；若同时想验 16:9，可在 MuMu 上再跑一场。
- 对局结束后记下会话目录名（`data/matches/<时间戳>/`）。

## 5. 已知坑（判读前先看）

1. **`MMTrackerV7.update()` 的 detect 结果缓存（已于 v15.4 修正：0.4s → 0.15s）**
   背景：v13.6 加缓存时 `detect()` ≈200ms，0.4s 窗口省 137ms/帧；现在 `detect()` 只有
   **22.7ms**（190px 小地图/576p），而 10-17 实测 `--capture scrcpy` 稳态 **3.5fps ≈ 286ms/帧**
   落在 0.4s 窗口内 → **46% 的帧拿到陈旧最多 400ms 的小地图**（塔位/敌方红点/野怪）。
   逐帧实测（`temp/_mm_cache_probe.py`，13 帧 576p）：

   | 帧间隔 | 场景 | 旧 0.4s 命中 | 新 0.15s 命中 |
   |---|---|---|---|
   | 280ms | scrcpy 3.5fps（当前生产） | **46%** | **0%** |
   | 450ms | screencap 2.2fps | 0% | 0% |
   | 100ms | 假设 10fps | 69% | 46% |
   | 0ms | 离线背靠背 | 92% | 92%（仍去重，符合原意） |

   输出正确性（10 帧 @280ms 与"直调 detect 该帧"比对）：旧窗口 **1/10 帧报错**
   （第 2 帧 BUFF 报 2、真值 3，取到上一帧），新窗口 **0/10**。

   - 判读影响：**当前生产帧率下第 ④/⑤ 项不再受缓存影响**，若仍恒定则是真问题
     （门控被关 / 门控过严 / 本局无该目标）。高帧率（>6.7fps）时缓存会重新生效。
2. **塔数 <10 是正常现象**（塔会被推掉），所以第 3 项看的是"最大值"而非中位。
3. **合成/回放数据**（`source != 'live'`）下第 6 项会降级为 INFO 而不是 FAIL ——
   技能状态由 m2 运行时写入，离线数据造不出来。
4. 对局进行中读文件可能碰到**半写行**，脚本会跳过并在头部显示计数。
5. 若真机布局变了（换设备/换模拟器），先用任务对齐标定器重标，别手改坐标：
   ```bash
   venv/Scripts/python.exe -X utf8 scripts/calibrate_minimap_box.py --write
   ```
   它以"20 个已知塔点的 `_tower_alive` 通过数"为目标函数，不依赖人工看图。

**④ 野怪：先被"总数有变化"骗过，逐点复核后推翻（v15.6 已处理）**。
只看总数会以为"恒 14 → {9,10}"就是门控生效；按点位拆开后（会话 `20261017_164149_269145`，305 帧）：

| 点位 | 证据出现率 | 性质 |

=> `dots.yellow` 的"变化"100% 来自 M4 一个点的闪烁，其余 13 点是常量。
**门控只是给常量换皮**，与 BUFF 同类，只是被总数变化遮住了。处置同 BUFF：
`MM_MONSTER_MODE="unavailable"`，输出空 + `monster_supported=False`（`dots.yellow` 同样无消费者）。

**并且用"正确点位"也救不回这个信号**：用下面标定出的 16 个真实营地点跑 `gated` 模式，
结果是**每帧恒为 16** —— 因为营地图标是常驻的，颜色判据永远看不到"怪死了"。
这从反面证明：需要的不是更准的坐标，而是**新的存活判据**（如图标中心的倒计时数字）。

**⑤ BUFF 门控无效 → 已于 v15.5 改为"诚实不输出"**：6 个 BUFF 点里 5 个在**每一帧都同时"有证据"**，
点位集合 1180 帧只有 1 种。放大取像素后看清原因：BUFF 点落在**常驻的橙色营地图标**上
（野区图标描边，永久绘制），而野怪点是小黄点（只在单位存活时出现）——
颜色在这两类点上无法区分"营地图标"与"在野 BUFF"，所以任何颜色阈值都只会得到新的常量。

修法（`MM_BUFF_MODE="unavailable"`，默认）：**不输出 BUFF**，并在输出里置
`buff_supported=False`，让下游能区分"未知"与"没有"。`"gated"`/`"fixed"` 保留作对照实验。
依据：生产路径**无人消费** `buff`（只有 legacy `mm_rules_v1..v6` 用），改动零风险。
若要真正恢复该信号，需要新判据（如"图标中心是否有倒计时数字"），不是调参能解决。

**复测（会话 `20261017_164149_269145`，305 帧）**：`buff_supported=False` 100%、`buff` 长度 0、
野怪仍为 {9,10}、塔 305/305 帧 10/10 → 全套 **PASS 5 / WARN 0 / FAIL 0，退出码 0**。

**红点 `dots.red`：查下去发现是"100% 误检"，已修（v15.7）**

原先记的是"覆盖率 4%（48/1180）"，看起来像召回低。逐帧取证后结论完全不同：

| 证据 | 结果 |
|---|---|

## 9. 野区营地点位标定（`scripts/calibrate_jungle_points.py`）

旧的 `MONSTER_PTS`(14) / `BUFF_PTS`(6) 与真机小地图**只有 5/20 能对上**（`M12` 偏 0.27、
`B4/B5` 偏 0.12），还漏了 12 个真实点位。已用算法重新标定，不再靠人工猜坐标。

**原理只有一条：时间稳定性。** 营地图标是常驻绘制的，几乎每帧都在同一像素位置；
英雄/小兵/野怪是移动的，不会反复命中同一像素。所以：

1. 每帧取金橙掩码 → 连通域 → 候选质心（过滤 8≤面积≤260、2≤边长≤16）；
2. 全部帧的候选点按半径 0.022 聚类；
3. 出现率 ≥ `--min-rate`（默认 0.4）→ 常驻结构；
4. 用**周围亮度**剔除 UI 叠层（队友头像是亮圆环）：实测真营地 V≤93.4、头像叠层 V≥103，
   阈值取 98（`--max-v`）。

**为什么 min-rate 取 0.4 而不是 0.9**：队友头像会**遮住**下面的营地。实测 15 号 3 个会话里，
被遮那一半的点出现率只有 0~10%，未被遮的是 100%，而它们在 17 号会话里都是 100% 且**坐标逐点相同**
（子集关系）→ 不是坐标漂移，是遮挡。遮挡不改变位置，所以放宽阈值能找回真营地；
移动单位不可能在同一像素反复出现，放宽不会引入假点（仍有亮度过滤兜底）。

**结果**（83 帧 / 5 个 1280×576 会话）：保留 **16 个**点位，**逐个目视核对**均落在金色营地图标上
（核图 `temp/_jungle_final.png`）；写入 `configs/jungle_points.json`，由 `mm_rules_v7.jungle_pts()` 加载。

**已知缺口**：暴君/主宰两个**大**图标不在表内 —— 灰色主宰不是金色（掩码取不到），
橙色暴君面积超出过滤窗口。这两者是战略目标，若要纳入需要单独一轮（面积上界放宽 + 非金色判据）。

> 用途声明：`jungle_pts()` 只表示"**此处有营地**"（静态结构），**不表示野怪存活**。
> 直接用它取代 `dots.yellow` 会得到恒定值 —— 已实测：`gated` 模式跑这 16 个点，每帧恒为 16。

## 10. 敌英红点：重做判据并通过真机验证（v15.9，10-18）

**背景**：v15.7/15.8 把 `dots.red` 判为"无精度无召回"并停用。10-18 拿到真实对局后重查，
发现根因不是"信号不存在"，而是**判据与画风不匹配**。

### 真机事实（1792 帧连续录制 `temp/_gt2.mkv`，1280×576）
- 小地图上的敌人 = **红圈包着头像的大圆盘**（半径约 10px@190，`RED_MM` 掩码面积 300~1500px），
  位置随移动变化 —— 4 帧目视 + 40 帧位置追踪都确认会动（x 从 0.478 走到 0.368）。
- 旧判据要求"红环 + **中心为空**（`CENTER_CAP`=0.15）"，而红圈里头像中心本来就红
  （实测真值点 `cen_map`=0.76）→ **每个真敌人都被拒**，这就是之前召回≈0 的原因。

### 逐层 A/B（179 帧采样，真值 = 红圈大盘）
| 配置 | 精确 | 召回 |
|---|---|---|
| 原判据（CAP=0.15） | 22% | 19% |
| 放宽 `CENTER_CAP`→0.95 | 45% | 20% |
| + 关 near_bad（塔/野点 17px） | 40% | 33% |
| + avatar 阈值 0.62→0.40 | 14% | 33% |
| **改判据：直接取"红圈大盘"(blob)** | **100%** | **100%** |

### 三处关键改动（均在 `mm_rules_v7.py`）
1. `MM_ENEMY_MODE="blob"` + `_enemy_blobs()`：`RED_MM` 掩码 → 连通域 → 面积 300~1600
   → 边界 / 圆盘(r≤112) / 停靠带过滤。旧环路径保留为 `"ring"` 仅作对照。
2. **`MM_RED_SUPPORTED` 恢复 `True`**。
3. **"红环互斥"只在 ring 模式启用**：它删除距队友/自己 15px 内的敌点，而团战时敌人本来
   就贴着队友 —— 实测**117 个有敌帧只剩 41 帧检出**，关掉后立即回到 117/117。
   这是召回从 35% → 100% 的唯一原因。

### 验证
- 精确 100%（121 TP / 0 FP）、召回 100%（117/117 有敌帧），与队友/自己重合仅 4/121（3%）。
- 目视复核：4 个检出点放大后**圈都是红色**（`temp/_blob_zoom.png`）；
  标注图 `temp/_blob_det.png`；面积判据图 `temp/_blob_check.png`
  （红塔图标约 210~240，与 300 阈值有干净间隔）。
- 回归：`test_new_modules.py` **198/198**、`test_laya_fusion.py` **56/56**（工作树；HEAD 53）。

> 真值口径：真值与检测器同用"红圈大盘"定义，故 100% 是**一致性**而非绝对真值；
> 语义正确性靠上述目视复核保证。若日后 UI 改版（头像变小/换色），需重新量 300~1600 区间。

### v15.9b：tracker 层也曾吃掉 84%（同一把尺子量出来的）

detect 修好后仍发现"线上红点稀"，于是把 **detect 与 tracker 分开量**（600 连续帧）：

| 层 | 精确 | 召回 |
|---|---|---|
| detect | 100% | 100% |
| tracker（修前） | 92% | **15%** |
| tracker（修后） | **99%** | **98%** |

元凶是 `_hero_result` 里的"静止即丢弃"：`age >= 6 且位移 < 1.5px` → 判为静物装饰。
30fps 下 6 帧只有 **0.2 秒**，英雄站着补刀/对拼就会被丢掉。A/B：

| `MM_TRK_STATIC_AGE` | 精确 | 召回 |
|---|---|---|
| 6（原值） | 94% | 14% |
| 30 | 98% | 40% |
| **0（关闭，现默认）** | **99%** | **98%** |

关键判断：这条规则是给**旧环检测器**的幽灵红环设的，而 blob 判据（面积 300~1600 +
圆盘/停靠带过滤）本身不产生幽灵点 —— 所以它对精确率**没有贡献**（关掉反而 94%→99%），
却吃掉了 84% 的真敌人。已改为默认 0 并注明来龙去脉。

> 教训：**必须分层量指标**。只量 detect 会以为"检测已 100%"，只量 tracker 会以为
> "检测器不行"—— 两者都错。

## 11. v16.0：血量读数修复 / self_present / 阈值去分辨率绑定

### 11.1 `ui.hp` 在 10-18 两局全空 —— 根因是"分段式血条 + y 带写死"

先排除代码回归：用 `git show HEAD:wzry/vision/self_bars.py` 单独加载跑同一批帧，
结果与当前版**完全一致**（10-17 帧 0.37 正常，10-18 两局都 `None`）→ 是画面差异。

放大帧后才看清：这版 UI 的血条是**分段式**——每隔约 10px 一道黑色刻度。
而 `_find_bars` 用 `MORPH_OPEN (21,1)` 过滤，绿色连续段不足 21px 就被**整条抹掉**
（实测该帧 0 条绿候选）。另外该帧自己血条在 **y≈206**，被写死的 `y>=250` 排除。
两道闸同时命中 → `hp` 恒 None。

修法（`self_bars.py`）：
1. `_find_bars(..., bridge=N)`：先做 `(N,1)` **闭运算**把被刻度切断的色段接回去（默认 0，不影响
   队友/敌人那两路）；`self_hp_mp` 传 `SELF_BAR_BRIDGE=13`。
2. `_find_bars(..., y_top=...)` 可按调用覆盖上界；`self_hp_mp` 改用**比例** 0.30h/0.96h。

实测（每局 4 帧）：

| 会话 | 修前 | 修后 |
|---|---|---|
| 20261017_162901 | 0.37 | 0.85 |
| 20261018_144334 | **None** | **0.59** |
| 20261018_144140 | **None** | **0.59** |

修后的 0.37→0.85 不是"变大了"，而是原来只量到被刻度切碎的一小段（42px）；
目视核对 `temp/_hp_check.png`：该帧血条确实接近满格，10-18 那帧是"约 60% 绿 + 40% 灰"→0.59。

### 11.2 `ui.self_present`（区分"我在打"与"我在看别人/已死"）

`m2` 在 `state_dict` 生成后追加：
`self_present = (hp 可读) or (小地图有自身绿点)`。
用于行为层避免拿"观战视角的血条"当成自己的血。

同时复测工具 ⑦ 的提示改为三分支（原来误用 `death_banner>0`，实际判死阈值是 **2500**）：
- `death_banner>=2500` 占多数 → 整局死亡（挂机）
- 全无自身绿点 → 非本人视角（观战/跨局），该会话不能用于血量判读
- 有自身绿点却读不到 hp → **疑似读数缺陷**

### 11.3 敌英 blob 面积阈值去分辨率绑定

原来 `MM_ENEMY_BLOB_MIN/MAX = 300/1600` 是 190px 小地图下的**绝对像素**，换分辨率就失效。
改为分位占比（`MM_ENEMY_BLOB_*_FRAC`），按当前小地图边长平方缩放。
校验：190px 处仍为 300/1600，指标不变（detect 100%/100%、tracker 99%/98%）。
（v16.0 全量复检后下限 300 → 170，见 §12.1，仍是占比形式。）
