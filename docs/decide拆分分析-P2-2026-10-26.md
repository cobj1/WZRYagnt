## 2. 为什么"四段"不可行

方案设想的形态是：

```python
def decide(state, cooldowns):
    obs = 观测过滤(...)      # 纯计算
    threat = 威胁评估(obs)    # 纯计算
    target = 目标选择(obs, threat)
    return 动作合成(target)
```

实际形态是：

```python
def decide(state, cooldowns):
    ...观测...
    if 条件A: cooldowns["x"] = now; return 动作1     # 段 16
    ...段 17 用到段 16 里算的 camp/fx/fy...
    if 条件B: cooldowns["y"] = now; return 动作2
    ...
```

三个硬事实：

1. **每段都可能提前 return**（`cooldowns["push_info"] = None` 的注释就写明"decide 在很多分支会提前 return"）。
   切成"四段各返回一个值"就必须让每一段都能短路，等于退回 if 链。
2. **段间共享局部变量**：段 0 定义的 `enemies/minions/allies/...` 被 9 个后续段引用；
   段 17 定义的 `camp/fx/fy` 被段 18 用。要切函数就得把这些塞进 ctx 或参数。
3. **副作用顺序**（写 `cooldowns`）：段内有多处 `cooldowns["recall_t"] = now`。
   把"先算全部再选一个"会**多写**冷却，直接改变下一拍行为。

## 3. 下一轮的可执行路线（按风险从低到高）

**不要按"四段"切，按"段"切。** 每段独立提取成 `_decide_<语义>(...) -> action | None`，
主函数变成 `for fn in stages: act = fn(...); if act: return act`。这样保持 if 链语义。

|---:|---|---:|---|---|---|

## 4. 本轮为什么没动 decide()

- 段 1/2 虽"低风险"，但提取后**总行数不减反增**（10 行函数 + 12 行解包 > 10 行原地代码），
  而收益要等到"整段搬去 policy_v2.py"才兑现；
- 收益真正大的是段 15/21-24，恰好是风险最高、最需要真机验证的四块；
- 方案 §4 P2 本身写的是"先分段确认 digest 不变，**下一轮**再整体搬到 policy_v2.py"。
  本轮已在 P1 建立了"搬运 + 闸门"的可复现流程，把 decide 留给有设备的一轮更划算。
