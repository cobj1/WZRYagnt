## 0. 测量口径（先读这一节，再读数字）

1. **同一进程内连续测量**（pid=53420，整轮 ov 与 e2e 都在这一进程里顺序跑），每格之间只做一次 `sess.run()` 计时，无 CPU 亲和性绑定、无进程优先级调整。

4. 因此 **ov 矩阵里的 L 是「实际有效输入 token 数」，不是模型计算量**：短输入由 shim 在 `_run_row()` 里 pad 到 512（`attention_mask` 置 0），K 同理补槽到 16。矩阵反映的是**不同有效输入长度下的端到端 shim 开销**（numpy pad/truncate + 一次固定 512 推理），**不是「模型按 L 变长推理」**——模型侧的计算量在 12 格之间完全相同。
5. 每格预热 5 次、计时 30 次；分位用线性插值（numpy 默认口径），与 40ms 的比较用未取整值。

## 3. 端到端决策延迟（历史 states 回放）

- 抽样：从 `data/matches/*/states.jsonl` 共 11043 帧中，按 `frames with units 非空 或 minimap.dots 有 red/blue/green 点` 过滤后剩 11039 帧，`random.Random(20261024).sample` 取 200 帧（覆盖 32 个会话）。
- 计时：`time.perf_counter()` 包住**单次调用**；hok 用的是 `HokShadow.decide()`（与生产 shadow 同款，含其内部落盘）；optimizer 用的是 `optimizer.solve(state, rule_fallback, hp, 'blue')`；串行列 = 同一帧上「先 hok 再 optimizer」的合计。
- **本节链路不含 laya/OV 推理**：脚本未调用 `optimizer.set_scorer()`，`optimizer._SCORER` 保持模块默认的 None；hok 侧 value model 是 `base_weights`。所以本节测的是**规则决策层**的耗时；「接上 laya 打分器后是否仍 ≤40ms」必须用第 2 节数字做叠加推算。
- 预算：G1 决策 40ms；主循环 5Hz → 每帧 200ms。

## 4. 结论：40ms 预算的达标边界

- **OVSession 推理单独看**：p95 最好的格是 GPU L=256/K=4 = 92.31ms，最差是 CPU L=64/K=8 = 1684.09ms（跨设备相差 18.2x）。
- 12 格 × 3 个可用设备中，p95≤40ms 的格共 0/36（无）。
  - CPU：p95 区间 1029.19–1684.09ms（12 格极差 654.90ms）→ **不达标**
  - GPU：p95 区间 92.31–100.70ms（12 格极差 8.39ms）→ **不达标**
  - NPU：p95 区间 418.55–432.58ms（12 格极差 14.03ms）→ **不达标**
- **L/K 对耗时几乎没有系统性的影响**：CPU 极差 654.90ms（1029.19–1684.09）；GPU 极差 8.39ms（92.31–100.70）；NPU 极差 14.03ms（418.55–432.58）。GPU/NPU 在 12 格之间几乎是平的（极差不到 15ms），说明 pad 量与 shim 的 numpy 开销相对固定 512/16 的计算量可以忽略；CPU 那档极差 655ms 属于测量噪声/负载抖动（同格 max 冲到 2043ms），不是 L/K 导致的——其**最小** p95 仍远超 40ms。**推论：缩短输入或减少选项救不了预算，只能换更小的模型，或把推理挪出决策临界路径。**
- **链路整体（全量抽样）**：串行 p95 = 20.25ms（p50 15.24ms，max 24.58ms），占 200ms 帧预算 10.1% → **达标**。
- 拆分：hok_bridge p50/p95 = 15.27/19.76ms，optimizer 全量 p50/p95 = 0.01/1.08ms、有红点帧 p50/p95 = 0.85/1.42ms —— 决策层的主要开销在 hok_bridge（beam search），不在规则优化器。
- **工作负载口径（53 个有敌方证据的帧）**：串行 p95 = 20.78ms，max 22.41ms → **达标**（这是更该用于 G1 判定的数字）。

### 判定

**G1（决策 p95 ≤ 40ms）只在「决策临界路径不含 laya 模型推理」的前提下成立。**两条测量给出的结论相反，引用时必须分开：
1. **含 laya 推理就必然不达标**：0/36 格 p95≤40ms。三块设备都编译成功、都跑完了 12 格（无失败项，不存在拿 CPU 数字冒充 GPU/NPU），但没有一块够用：最快的是 GPU 的 p50 90.01ms / p95 92.37ms，NPU p50 约 415ms，CPU p50 约 1.0–1.4s。最坏一格（L=512,K=16）见第 2 节。
2. **把 laya 同步串进链路会直接翻车**：规则链路 p95 20.78ms + 最快设备单次推理 p50 90.01ms（GPU）≈ 111ms，是 40ms 预算的 2.8 倍。e2e 数字之所以好看，是因为脚本里 `optimizer._SCORER` 为 None、整条链路根本没跑 OV 推理（见第 3 节说明）——这一点不能被误读成「接了 laya 也 20ms」。
3. **规则决策层本身达标**：hok_bridge + optimizer 串行 p95 = 20.78ms，占 200ms 帧预算 10.4%，余量约 179ms。
4. **G1 达标的前提**（按重要性排序）：
   - laya 打分器必须走**异步旁路**（像 `HokShadowWorker`：低频、可丢弃、不阻塞主循环），其耗时不计入 40ms 决策预算。这是唯一能让 G1 成立且保留模型的路径。
   - 若业务上必须同步打分，则只能换模型规模：本 IR 固定 512/16、842MB bin，最快设备也要 ~92ms；调小 L/K 无效（见本节上一条）。
   - 上述数字是**本机、同进程顺序测量**的分位；真机还要叠加采集/视觉/编码，G1 闸门最终必须用真机同进程端到端埋点复核。
