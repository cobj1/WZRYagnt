# 检测器阵营抖动：量化与修复（2026-10-28）

> **结论**：抖动已量化并定位到 `camp_src=default` 兜底路径（占翻转的 **88.5%**）；
> 时序投票修复能把翻转率从 **1.79% 降到 0.23%（−87.3%）**，只改 682/25,266 个单位。
> **但应用后决策 digest 从 `90c1a9af` 变为 `e34ef6b8`**，按仓库纪律已回滚 ——
> 因为顺带暴露出一个更值得修的缺陷：**决策层对 `ally_hero` 不做可信度过滤**（见 §四）。

---

## 一、问题

审计 A2 遗留项：同一静止英雄（绿血条）在连续帧被判敌/友两种
（`20261020_224657_708566` frame_000002 / 000004）。
`camp_correct` 用血条颜色探针判敌/友，探针取不到条时落 `default` 兜底。

阵营是训练标签里最大的两类之一，抖动直接污染 `ally_hero` / `enemy_hero` 监督。

## 二、量化（`scripts/eval_camp_jitter.py`）

全库 51 会话、英雄单位（`cls ∈ {ally_hero, enemy_hero}`）：

| 指标 | 值 |
|---|---:|
| 英雄单位总数 | **25,266** |
| `camp_src = bar`（血条探针） | 17,860（70.7%） |
| `camp_src = default`（**无证据兜底**） | **6,603（26.1%）** |
| `camp_src = color` | 163 |
| `camp_src` 缺失（`None`） | 640（2.5%） |
| 相邻帧配对（IoU ≥ 0.5） | 23,356 |
| **阵营翻转** | **418 → 1.79%** |

翻转按来源归因（这是关键）：

| 组合 | 次数 | 占翻转 |
|---|---:|---:|
| `default ↔ default` | **267** | 63.9% |
| `bar ↔ default` | 68 | 16.3% |
| `bar ↔ bar` | 46 | 11.0% |
| `None ↔ None` | 35 | 8.4% |
| `color ↔ color` | 2 | 0.5% |

**涉及 `default`/`None` 的翻转 = 370 / 418 = 88.5%。**
即抖动几乎全部来自"没有证据、按检测器逐帧类别兜底"的路径 —— 兜底本身不稳定。

## 三、修复（`scripts/relabel_camp_temporal.py`，默认 dry-run）

做法：同会话内按屏幕框 IoU + **中心位移门限**把单位串成轨迹；
轨迹内若有可信来源（`bar`/`color`/`memory`）的帧，取其多数票覆盖不可信的帧；
整条轨迹都不可信时取全轨迹多数票。**可信帧永不改写**。

| 指标 | 改前 | 改后 |
|---|---:|---:|
| 阵营翻转 | 418 / 23,356 = **1.79%** | 53 / 23,356 = **0.23%** |
| 改写单位数 | — | **682 / 25,266 = 2.7%** |
| 跳过（可信来源帧） | — | 124 |

改善 **−87.3%**，代价只有 2.7% 的标签被平滑，且原值保留在 `cls_raw`、标记 `camp_vote="temporal"`。

> 位移门限（`--max-shift`，默认 0.15 归一化）是为了防止"两个英雄交错走过"被 IoU 串成
> 同一条轨迹，从而让多数票互相覆盖。本批数据下它没有改变结果（IoU≥0.5 已隐含小位移），
> 属防御性约束。

## 四、为什么没有落地（重要）

应用后跑 `refactor_gate`：

```
digest 90c1a9afa4737f6e → e34ef6b8bb0371b7   （FAIL：决策 digest 变化）
```

**根因**：`wzry/vision/hok_yolov5.py` 注释写着"保守判敌 + camp_src=default（下游按不可信过滤）"，
但**过滤只在敌方向上做了**：

| 位置 | 行为 |
|---|---|
| `decision/optimizer.enemy_hero_trusted` | `cls == enemy_hero` **且** `camp_src ∉ UNTRUSTED` → 才采信 ✅ |
| `decision/context.py:52` | `cls == enemy_hero` → 走 `trusted()` 检查 ✅ |
| `decision/context.py:56` | `cls == ally_hero` → **直接 append 到 `view.allies`，无任何可信度检查** ❌ |

所以一个 `camp_src=default` 的框：判敌 → 被过滤（不参与决策）；判友 → **被当成队友采信**。
时序投票把它从"友"改成"敌"时，它就从 `view.allies` 里消失 —— 决策因此改变。

这违反项目自己的 S0-2 原则（"不可观测 ≠ 观测为 0"），且是**不对称**实现的：
不可信的敌被丢弃、不可信的友被采信。

## 五、结论与待办

1. **两项修复都已就绪，但都改变决策**，需要真机 A/B 才能接管：
   - ① 时序投票重标注（标签侧，−87.3% 抖动，可一键回滚）；
   - ② `context.py` 的 `ally_hero` 补可信度过滤（对称化）。
2. **②更根本**：它不依赖任何新数据，是纯逻辑缺陷。但同样会改变"队友在附近"类判断，
   需与 ① 一起在真机上验证（建议先 ② 后 ①，因为 ① 的正确性依赖 ② 的语义一致）。
3. 当前基线已回滚（digest `90c1a9af`、翻转率 1.79%），`data/matches/` 未残留改动。
