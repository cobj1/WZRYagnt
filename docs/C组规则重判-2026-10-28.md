## 三、由重判得到的三条新事实

### 1. 动作码字段的取值空间**大于 19**

`#46` 写 `mov w8, #0x1e`（30）到同一个 `result+0x150`。所以
`docs/动作码对照表-2026-10-28.md` 的"19 个码"应理解为
**双手动作（Atk*）标签子集**，而不是字段的全部取值。字段还承载其他动作族
（`UseMapSpecialSkill` 一类，码 30）。`action_codes.label_of_code(30)` 返回 `None`
是正确行为，但不要据此认为数据异常。

### 2. `#2` 是"打塔"规则，语义已完整可读

```
0x27ea7b8  ldr w8,[x0+0x1604]; cmp #1; b.ne 返回 0      ; 规则启用开关
0x27ea7c4  ldr w8,[x1]                                  ; 当前帧号
0x27ea7c8  ldr w9,[x2+0x15f4]                           ; 上次施法帧
0x27ea7cc  ldr w10,[x0+0x13d8]                          ; 冷却帧数
0x27ea7d0  sub w8,w8,w9 ; cmp w8,w10 ; b.le 继续         ; 帧差 ≤ 冷却才触发
0x27ea7e4  ldr x8,[x0+0x900]                            ; self 单位
0x27ea7e8  ldr w9,[x8+0x18]                             ; 单位状态
0x27ea7ec  ldr w8,[x2+0x15c8]                           ; 技能槽/技能 id
        按 (状态==1?, 技能==5?) 四选一，取常量表
        0x542b590 / 0x542b428 / 0x542b59c / 0x542b434
0x27ea848  str x9,[x2+0x170]  str w8,[x2+0x178]         ; 写入预设走位点
0x27ea85c  str w8=13,[x2+0x150]                         ; 动作 = AtkTowerSkill2
```

即：**技能未产生位移时，把走位目标换成预设点，并用技能 2 打塔**。

### 3. 字段依赖是硬约束，不是可以绕过的细节

| 指标 | 值 |
|---|---:|
| 16 条规则引用的不同 `(寄存器,偏移)` | **120** |
| 其中 self/ctx 侧（`x0`/`x8`/`x9`）不同偏移 | **84** |
| `configs/mem_offsets.json` 已覆盖 | **5**（`+0xc` / `+0x10` / `+0x18` / `+0x388`） |
| 未覆盖 | **79** |

> 注：`x8`/`x9` 有时是临时指针（如 `x8 = self+0x900` 后再取 `[x8+0x18]`），
> 因此 84 这个数**偏高**；但量级结论不受影响——规则依赖的状态面远大于我们当前建模的。

**按热度排序后，没有"一次补齐"的捷径**（下表已按寄存器归属核实，剔除临时寄存器误报）：

| 引用 | 被几条规则引用 | 语义 | 我们是否有 |
|---|---:|---|---|
| `x0+0x900` | 7 | self 单位指针（再取 `+0x58` hp / `+0x60` hp_max） | ✅ 有（`self_state.hp`） |
| `x8+0x58` | 4 | 单位 hp（`x8` 来自 `x0+0x900`） | ✅ 有 |
| `x8+0x18` | — | 单位状态（`x8` 同上） | ⚠️ 部分（`skill_off_state`） |
| `x0+0x388` | 4 | actor_mgr | ✅ 有 |
| `x8+0x70` | 8 | **临时寄存器误报**（`[sp,#0x70]` 一类），不是 self 字段 | — |

即：**高频项其实都已在覆盖内**，剩下的是"每条规则各自的少数专用状态字段"
（如 #2 的 `+0x1604` / `+0x15f4` / `+0x13d8` / `+0x15c8`，#11 的 `+0x152c`）。
这类字段**无法集中补齐**，只能按规则逐条做，且偏移语义必须真机对账 —— 这正是代价所在。

## 四、结论与下一步

**不要继续逐条 RE。** 三条前置已通，但每条规则平均要 11–23 个内部字段，
按现有 `Snapshot` 覆盖率强行实现只能写出"永远不触发"的惰性规则（与
`WaitResurrectionArmor` 现状相同），投入产出不划算。

正确的顺序调整为：

1. **不再追"热字段"**（上一节的核实已否定这条捷径）：高频项已在覆盖内，
   剩下的是每条规则各自的专用字段（`+0x1604`/`+0x15f4`/`+0x13d8`/`+0x152c` …），
   只能按规则逐条补。
2. **补字段必须真机对账**：`mem_offsets.json` 里的偏移只能在局内验证
   （内存直读 vs HUD / 小地图 / 技能 CD），当前 `adb devices` 为空 → **阻塞**。
3. 字段到位后规则实现反而快（动作码、阈值、分支结构都已明确）。

**因此 C 组的状态从"缺技术手段"改为"缺数据通道"，且该通道受设备阻塞。**
设备回来后的第一批工作应是：#2（51 指令，字段最少且语义已完整读出）→ #11 → #22。
