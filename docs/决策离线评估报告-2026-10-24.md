## 3. 指标定义（精确）

**动作类型维度**：两条路径归一成 3 类后比较——

| 粗类 | 规则侧（optimizer 候选 type） | 模型侧（hok ActionKind） |
| --- | --- | --- |
| `engage`（交战） | `skill`, `attack`, `combo` | `attack_enemy` |
| `move`（位移/战术） | `map_move`, `recall`, `restore` | `retreat`, `capture_resource`, `defend_tower`, `push_tower` |
| `none`（无动作） | `none` | 无决策/空动作 |

> 只在粗粒度上算一致率是**方法上的让步**：hok 的动作空间是宏观动作，没有技能/普攻级粒度，
> `skill` 与 `attack` 无法与模型侧对齐。细粒度组合只作为诊断列给出，不参与任何一致率分子。

**目标维度**：动作意图落点统一到小地图归一化坐标 `[0,1]²` 后比距离——

- 规则 `map_move` → `(nx, ny)`；
- 规则 `skill`/`attack`/`combo` → **距自己最近的红点**（小地图代理：这类候选只由"屏内最近敌英"生成，而 `units` 只有屏幕坐标、没有小地图坐标，无法精确投影；该代理是本次评估的已知误差源，见 §9）；无红点时为 `None`；
- 规则 `none` → `None`；
- 模型 `target_position`（hok ref_416x424）→ 用 `hok_bridge.MINIMAP_AFFINE` 反算回归一化坐标；无目标时为 `None`。

"同目标" = 两点欧氏距离 ≤ **0.15**（归一化地图单位）**或两侧皆 `None`**；一侧 `None` 另一侧非 `None` 判为不一致。

**一致率**：模型首选（`first_kind`）是否落在规则排序 top-k 的同一维度内；`strict` = 类型与目标同时命中。分母是**两侧都产出动作**的帧数（本次 10654 帧）。模型报错/空动作的帧不进入分母，也**不按"回退到规则"记一致**。
**翻转率** = 粗类不一致帧数 / 分母。翻转方向 = `规则粗类->模型粗类` 计数。
**延迟**：`time.perf_counter()` 单帧实测，分位用 nearest-rank（升序后取 `idx=ceil(p*n)-1`）。`规则` = `_feat`+`gen_candidates`+排序+`solve()`；`模型` = `HokShadow.decide()`（含桥接建态 + beam search + DecisionOutput 落盘）；`全链路` = 单帧 dict 输入到两条决策完成并比对，**不含** JSON 反序列化。

### 7.1 hok_bridge 在历史 states 上的失败模式

本次 11043 帧中，hok_bridge 抛异常/返回空动作 **389 帧**（3.5%）。

**失败模式分布**（按报错文本归类，全部是"不抛异常、返回空动作"）：

| 错误类别 / 文本 | 帧数 | 占评估帧 |
| --- | --- | --- |
| `EmptyDecision: 小地图无己方色点(绿/蓝皆缺), 建不出己方 Hero` | 389 | 3.5% |

根因（读代码可确认，不是猜测）：`_hero_rows()` 在 `units[*].pos_minimap` 缺失时只认 `minimap.dots`；再经 `_camp_of()`（缺 `self_state` → 恒 `blue`）分流后，若本帧没有任何绿/蓝色点，就建不出 `side=blue` 的 Hero，`generate_candidates()` 因 `next(alive blue)` 为 `None` 返回空列表，`beam_search` 于是没有候选可搜 → `first_kind=None`。**这类帧模型必然沉默，只能靠规则层兜底**，属于域不匹配而非偶发故障。

另一个方向："不报错"也不等于"域对齐"。以下三项是**实测的静默降级**（桥接器有回退分支，不会抛异常，所以指标看着正常、语义已经变了）：

| 桥接依赖字段 | 覆盖帧 | 桥接的回退行为 | 后果 |
| --- | --- | --- | --- |
| `self_state`（己方阵营/血量） | 0 | `_camp_of()` 恒返回 `blue`；`_hp_ratio()` 取不到血量 → 1.0 | 模型永远认为**自己满血**，且把蓝方当自己 |
| `units[*].pos_minimap`（单位小地图坐标） | 0 | `_hero_rows()` 回退到 `minimap.dots` 色点 | 英雄身份靠色点顺序，无 uid / 无真实血量 |
| `clock_s` / `game_time_s` / `ui.match_clock`（对局时钟） | 0 | `_game_time()` 恒返回 0.0 | `game_time=0` → 龙的刷新门恒不满足、价值上下文的时间项失真 |

另一条可用证据：**死亡/黑屏**桶 405 帧里，模型仍然每帧都产出动作（`capture_resource` 195、`retreat` 182、`attack_enemy` 17），因为桥接器不读 `behavior.dead`、也被 `hp=1.0` 兜住 —— 死亡期间模型仍在推进/打野。这类帧的 agreement 没有决策意义，只说明状态域没对齐。

动作分布集中度：模型首选 `push_tower` 占 46.5%（见 §4 分布表）。集中度过高通常意味着模型没有真正被状态区分开，而是被少数固定目标（塔/野点）主导。

## 9. 已知偏差与后续

1. **无人类标签，只能测"一致性"不能测"正确性"**。agreement 高只说明两套系统彼此接近，不说明决策对。要回答"谁更好"需要结果回溯（击杀/推塔/存活）或人工标注，本闭环不提供。
2. **比较粒度被 hok 的动作空间限制在 3 类**。`skill`/`attack` 与 `attack_enemy` 只能合并成 `engage`，所以类型一致率天然偏乐观；严格口径（类型+目标）更有区分度。
3. **hp 缺失 4554 帧按 1.0 兜底**（占可评估帧 41.2%）。这些帧永远进不了 `残血` 桶，也永远不会触发 optimizer 的 `hp<0.5` 保命过滤 —— `残血` 桶的样本量因此只来自有 hp 的会话。
4. **规则侧技能/攻击的目标是小地图代理**（最近红点），而模型侧是真 `target_position`。目标维度对 `engage` 类帧的一致率因此偏保守，误差量级可用 §4 的目标距离 p50/p90 判断。
5. **单帧独立评估**：不含时序、冷却、技能可用性（`ui.skill1_ready` 等仅 1420 帧有），规则层与模型层都是"看这一帧算这一帧"，不比多步连贯性。
6. **状态采集约 8.4Hz（会话中位 dt≈0.12s），而生产里 hok 以 1–2Hz 被调用**。逐帧评估测的是单次决策成本，不代表生产占空比；延迟要看 p95/p99 而不是总时长。
7. **分桶阈值是手写常数**（`TEAM_RADIUS`/`MINION_N`/`LOW_HP` 等），没有在标注集上校准过；红点/敌兵检测的漏检会把这些帧降级进 `游走`，导致 `游走` 桶混入团战帧。
8. **规则兜底动作是评估脚本自造的替身**（"走向己方绿点"）。生产里 `m2_agent_v2` 传给 `optimizer.solve` 的是规则层自己算出的 `map_move`，脚本拿不到那一路，所以 `规则层下放率` 只能当相对量看（它主要反映"`solve()` 有没有覆盖兜底"，而不是"规则层做了多少决策"）。另外也不能传 `{"type": "none"}` 当兜底——`_solve_core` 的动作白名单含 `none`，会原样返回，等于规则层完全不决策。

后续可做：把 `hok_bridge` 的 `self_state` / `pos_minimap` / `clock_s` 三个字段补进记录器，再重跑本脚本，即可量化"域对齐"对一致率的增益；以及接入结果回溯标签，把一致性换成胜率/收益。
